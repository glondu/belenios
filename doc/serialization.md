# Serialization

Belenios values are converted to and from JSON through *type
descriptions*: values of type `'a Desc.Core.t` that describe the
structure of an OCaml type `'a`. Interpreters walk these descriptions;
today there is one, the canonical JSON interpreter `Desc.Json`.
Others (a schema or documentation generator, a binary format) can be
added without touching the types.

Descriptions are generated by the in-house ppx `ppx_desc`
(`[@@deriving desc]`), or written by hand for abstract types.

History: up to 3.3.0, Belenios used atdgen (`.atd` files); the
development version then used ppx_yojson_conv. Both generate opaque
converters, and ppx_yojson_conv lost the language-independent
description that the `.atd` files provided. 4.0.0 breaks
compatibility with both: it does not read data produced by earlier
versions.

## Constraints

- **Exact bytes matter.** Many JSON objects are hashed:
  - over their raw bytes: archive payloads and events, ballots, the
    election fingerprint;
  - over a value encoded again after decoding (`Hash.hash_desc`): the
    voter list, trustees' `coefexps`, the encrypted tally, etc.

  So the encoder must be deterministic, and decoding then encoding a
  value produced by Belenios must give back the same bytes.
- **Abstract types** (group elements, scalars, hashes, UUIDs…) are
  described by hand, usually as a `map` over `string`.
- **Types parameterized by a group**: the description of
  `('elt, 'scalar) foo` is a function
  `'elt t -> 'scalar t -> ('elt, 'scalar) foo t`.
- Descriptions are shared between the server, the command-line tool
  and the browser clients (js_of_ocaml), where OCaml `int` has 32 bits.

## JSON format

The encoder (`Desc.Json.to_json`) is canonical: one representation per
value. Output is printed compactly by `Yojson.Safe.to_string`.

| OCaml | JSON |
|---|---|
| `unit` | `null` |
| `bool` | boolean |
| `int` | integer |
| `int64` | integer (see below) |
| `string` | string |
| `'a list`, `'a array` | array |
| tuple | array, of fixed length |
| record | object, fields in declaration order |
| constant constructor `A` | `"A"` |
| constructor with one argument `B of x` | `{"B":x}` |
| constructor with several arguments `C of x * y` | `{"C":[x,y]}` |
| constructor with a tuple argument `D of (x * y)` | `{"D":[x,y]}` |
| constructor with an inline record `E of {a; b}` | `{"E":{"a":…,"b":…}}` |
| maps (`SMap`, `HMap`) | object, keys sorted in byte order |
| association lists (`languages`…) | object, keys in list order |
| `'a option` as a value | `null` for `None`, the value for `Some` |

Polymorphic variants use the same representation as regular ones.

Details:

- **Optional fields** (record fields of type `_ option`) are left out
  when `None`, never written as `null`. Fields with a default value
  (`[@default e]`) are left out when equal to `e`.
- **64-bit integers** are plain JSON integers. Every value Belenios
  produces stays below 2^53, so all JSON readers handle them exactly.
  Values that can exceed 2^31 (weights, times) must be `int64` on the
  OCaml side. Under js_of_ocaml, an `int64` that does not fit in an
  `int` is written through Yojson's `Intlit`.
- **Times** are `int64` seconds since the Unix epoch. There are no
  floats in the format.
- **`option` inside `option`** is refused when the description is
  built (`Desc.Core.Invalid`), as is `option` over any description that
  can already produce `null` (`unit`, raw JSON). An optional field of
  type `_ option option` is fine: absent, `null` or a value.
- **Untagged unions** (`Shape.t`): each case is written as its argument
  alone (`Array` as a JSON array, `Atomic` as the value itself).
  Decoding picks the case by JSON kind; overlapping cases are refused
  when the description is built.
- **Questions** keep a specific representation:
  `{"type":"Homomorphic","value":{…},"extra":{…}}`. `type` and `value`
  are the cryptographic part; `extra` is an optional annotation for
  rendering and counting (`type`, `method`, `blank`, `grades`,
  `seats`), kept as raw JSON.

## Decoding

The decoder (`Desc.Json.of_json`) is tolerant where this does not
change the decoded value:

- key order does not matter;
- unknown fields are ignored;
- an explicit default value is accepted (and left out on re-encoding);
- keys of a sorted object may come in any order (they are sorted on
  re-encoding);
- an `int` may come as an `Intlit` that fits (for producers other than
  Yojson).

It is strict otherwise:

- duplicate keys are rejected, since the value would depend on which
  occurrence is read;
- `null` for an optional field is an error (the encoder never writes
  it);
- integers out of range are errors.

Errors raise `Desc.Json.Error (path, message)`, where the path locates
the faulty value, e.g. `questions.2.answers: missing field "x"`.
`Failure` and `Invalid_argument` raised by hand-written conversions
(`map`, `custom`) become decoding errors at the current path.

## The `desc` library

`src/lib/desc`, public name `belenios-lib.desc`. It depends only on
Yojson and does not depend on the rest of Belenios.

- `Desc.Core`: the description GADT and its smart constructors.
  - Base types: `unit`, `bool`, `int`, `int64`, `string`, `json` (any
    value, kept as is).
  - Containers: `list`, `array`, `option`, `assoc`, `sorted_assoc`.
  - Tuples: `tuple` (general form, used by the ppx), `tup2`…`tup5`.
  - Records: `record` over fields built with `field`, `optional` and
    `default`.
  - Variants: `variant` and `untagged`, over cases built with `const`
    and `case`.
  - `map base inj prj`: a type represented as another one.
  - `custom name to_json of_json`: hand-written JSON converters, opaque
    to other interpreters. Use only when no other construct fits.
  - `fix name f`: recursive types.
- `Desc.Json`: the canonical JSON interpreter (`to_json`, `of_json`,
  `to_string`, `of_string`).

The GADT is `private`: interpreters match on it, but descriptions are
only built with the smart constructors, which check the invariants
(no duplicate field names or tags, no ambiguous `option`, disjoint
`untagged` cases) and raise `Desc.Core.Invalid` otherwise.

### Recursion

`fix` builds a named `Rec` node whose body is a `lazy` value:
`let rec` on values refuses function calls, but always accepts `lazy`.
The node is shared by all occurrences, and the name lets interpreters
that walk the description itself (rather than data) emit a reference
instead of looping.

`fix` forces the body before returning, so no unforced `lazy` escapes:
this matters with OCaml 5 domains, where concurrent `Lazy.force` can
raise `Lazy.Undefined`. `f` must only reference its argument, not
inspect it; otherwise `Lazy.Undefined` is raised, deterministically,
when the description is built.

Interpreters must not keep global mutable caches (e.g. memoizing a
compiled encoder by `Rec` name), for the same reason.

## `ppx_desc`

`src/ppx_desc`. For a type `('a, 'b) foo` with `[@@deriving desc]`, it
generates

```ocaml
val foo_d : 'a Desc.Core.t -> 'b Desc.Core.t -> ('a, 'b) foo Desc.Core.t
```

- A type `M.bar` is described by `M.bar_d`. `int`, `int64`, `string`,
  `bool`, `unit`, `list`, `array` and `option` map to the functions of
  `Desc.Core`.
- Supported: aliases, tuples, records, regular variants (including
  inline records), polymorphic variants, and self-recursive types
  (through `fix`).
- Record fields of type `_ option` are optional.
- Attributes on record fields: `[@key "name"]` (JSON key, when it
  differs from the OCaml name), `[@default e]` (left out when equal to
  `e`, compared with `( = )`).
- Rejected with an error: abstract and open types, GADT constructors,
  functor applications, mutually recursive types, polymorphic
  recursion.

`[%desc_of_group: _ M.foo]` expands to `M.foo_d G.t_d G.Zq.t_d`: the
description of a type parameterized by group elements and scalars,
instantiated with those of the module `G` in scope. `G.t_d` and
`G.Zq.t_d` come from the `GROUP` and `FIELD` signatures.

## Hand-written descriptions

Abstract types define their description next to them, usually with
`map` over `string` (`Uuid.t_d`, `Hash.t_d`, group elements and
scalars) or over a described type.

`custom` is used where decoding depends on a value read earlier,
e.g. on the group: the types wrapped on the group
(`wrapped_draft_election`, `wrapped_credentials_params`,
`wrapped_trustees_status`). Types dispatched on the `version` field
only use `map` with a version check, and `Election.t` is a
hand-written wrapper around a described `params` record. Other places
that need the group take it from context.

## Helpers

In `src/lib/core`:

- `!* d s` decodes the string `s` with description `d`; `!+ d x`
  encodes `x`.
- `Hash.hash_desc d x` hashes the canonical encoding of `x`.
- `'a exchangeable = { dst; desc }` pairs a description with the domain
  separation tag used when signing or encrypting such values between
  trustees (`Pki`).

## Tests

- `dune runtest src/lib/desc`: unit tests of the library (encoding,
  decoding, errors, invariants).
- `tests/serialization`: `make check` runs `check-archives.sh` on the
  `.bel` archives produced by the `tests/tool` scenarios. Every data
  and event file is decoded with its description and encoded again,
  and the result must be the same bytes. The file hashes are checked
  too.

  `Rec` and `Custom` have one).
- Errors inside question `value`s lose their path, since `value` is
  decoded in a second pass.
- `doc/specification.tex` describes the format by hand; it could be
  generated from the descriptions.
